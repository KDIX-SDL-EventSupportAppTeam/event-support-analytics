# 交絡要因と統制方法

**最重要。この文書を読まずに分析結果を解釈してはならない。**

素直に集計すると誤った結論に至る箇所を列挙する。

---

## 交絡1: クールタイム設定が期間中に変更された

### 何が起きたか

去年のアプリには、連続チェックインを防ぐクールタイム（`COOLDOWN_SECONDS`）があり、
**この値がイベント期間中に変更されている。**

去年のリポジトリの git 履歴から確認された値の変遷:

| コミット日時 | 値 |
|---|---|
| 2025-10-07 22:21 | 3秒（開発中の値） |
| 2025-10-09 16:26 / 22:54 | **180秒（3分）** ← 本番直前に設定 |
| **2025-10-10 20:08** | **60秒（1分）** ← 初日の夜 |

### 記録と証言の食い違い

- **git 履歴**: 180秒 → 60秒への短縮。記録された変更は初日夜の1回のみ
- **運営の記憶**: 初日の最初は60秒で、日中のどこかで大幅に短縮した

**両者は値において一致しない。**

ただし**コミット時刻はデプロイ時刻ではない**。
当日その場で修正・デプロイし、コミットは夜にまとめて行った、
という流れは十分ありうる。20:08 というコミット時刻もそれを示唆する。

### 統制方法: データから変更点を特定する

**記憶にも git 履歴にも頼らない。** クールタイム値は
チェックイン間隔の下限として、データに直接刻まれている。

> 30分刻みのビンごとに、`visits.gap_min` の
> **最小値**と**5パーセンタイル**をプロットする

クールタイム値がそのまま床として現れるため、**階段状の段差が変更時刻**である。

この算出は他のどの分析よりも先に行うこと。結果を
[metrics-catalog.md](metrics-catalog.md) の E-2 / E-3 の前提として使う。

### 統制の前に: 交絡の大きさ自体を測る

**クールタイムが分析を歪めるのは、参加者が実際に制約に張り付いていた場合だけである。**

仮にチェックイン間隔の中央値が8分なら、床が60秒でも180秒でも
分布はほとんど影響を受けず、この交絡は無視できる。

したがって E-2 / E-3 に入る前に、次の1つの数字を出す。

> **全チェックイン間隔のうち、その時点の床から +20% 以内に収まっている割合**

| 結果 | 判断 |
|---|---|
| **数%程度** | クールタイムは無視してよい。E-2 の中央値は実質滞在時間として読める |
| **20〜30%以上** | 参加者は制約いっぱいで回っていた。E-2 は仕様の天井を測っているに過ぎず、真の値は測定不能。**「少なくとも X ブース/時以上」という下限としてのみ使える** |

後者の場合、**E-3（後半にペースが落ちるか）は結論を出せない。**
時間帯によるペース変化とクールタイム短縮によるペース変化が、同一時刻で交絡するため。

**切り分けの唯一の方法は、クールタイム値が終日一定だった土曜のみで E-3 を見ることである。**

## 交絡2: 開催日数の差（2日間 → 1日）

### 問題

去年は金・土の2日間、今年は金曜のみ。
以下の2つの要求が衝突する。

- **代表性**: 今年は金曜開催 → 去年の**初日（金）**が最も比較可能
- **クリーンさ**: クールタイム変更があったのは初日 → **土曜**の方が交絡がない

### 統制方法: 指標ごとに使い分ける

| 指標の種類 | 主分析 | 理由 |
|---|---|---|
| チェックイン間隔に依存（E-2 / E-3） | **土曜** | クールタイム値が一定 |
| それ以外すべて | **初日（金）** | 今年との比較可能性 |

**両日の結果を必ず併記すること。**
片方だけを示すと、読者は差の存在に気づけない。

### 副次的な問題: 曜日による来場者層の差

土曜は一般来場者・家族連れの比率が上がると予想される。
土曜のデータをそのまま今年（金曜開催）の予測に使うと誤る可能性がある。

**両日の属性分布（`age` / `gender` / `genre`）を比較し、
差の大きさを確認してから土曜データの利用範囲を決める。**

### 規模の比較における注意

**302名は2日間の延べ登録者数である。**
今年の見積もり「150〜200名」と直接比較してはならない。

必ず日別に分解し、**初日のみの登録者数**と比較すること。
仮に初日150名・2日目150名であれば、今年の見積もりはむしろ妥当となる。

## 交絡3: 滞在時間の系統的な過小評価

### 問題

入退場時刻が記録されていないため、
滞在時間を「最終チェックイン − 初回チェックイン」で代用している。

これにより以下が失われる。

- 受付から初回チェックインまでのラグ
- 最終チェックインから退場までのラグ

**算出される滞在時間は、真の滞在時間の下限である。**

### 統制方法

**補正しない。** ラグの分布が不明なため、補正すると恣意的になる。

代わりに、結論の書き方を統一する。

> 誤: 「30分未満の参加者が X% だった」
> 正: 「チェックイン記録上の滞在時間が30分未満の参加者が X% だった（真の滞在時間はこれより長い）」

### 単発訪問者の扱い

1ブースのみの参加者は滞在時間が定義上 0 になる。

**滞在時間の統計量（中央値・平均・四分位）からは除外する。**
0 が大量に混入すると分布が歪む。

**代わりに人数と割合を別枠で報告する（A-4）。**
滞在時間の分布に混ぜず、独立した数字として扱う。

## 交絡4: タイムゾーン

### 問題

Firestore のタイムスタンプは**すべて UTC** で保存されている。

変換を忘れると時間帯別分析（B系列）が9時間ずれ、
「開場前にピークがあった」という不合理な結果になる。

### 統制方法

**抽出直後の中間テーブル生成時に、一括で JST へ変換する。**
以降、UTC の値は保持しない。

`day` の判定も JST 変換**後**に行う。
UTC のまま日付を取ると、日本時間の朝9時前のチェックインが前日に分類される。

## 交絡5: テストデータの混入

### 問題

`(default)` にはイベント後（10/27以降）に作られたテストアカウントが含まれる。

### 統制方法

イベント期間外のタイムスタンプを持つレコードを機械的に除外する。
詳細は [exclusion-rules.md](../03-extraction/exclusion-rules.md) を参照。
