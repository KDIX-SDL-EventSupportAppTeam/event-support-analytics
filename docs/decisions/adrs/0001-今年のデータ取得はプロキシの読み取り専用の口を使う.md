# ADR 0001 — 今年のデータ取得は、さくらプロキシに読み取り専用の口を足して使う

- **状態:** 採用
- **日付:** 2026-08-31
- **対応する未確定項目:** [E-1](../../specs/recommendation-evaluation/README.md)
- **関連:** `event-support-recommend` ADR 0002（同じ問題。こちらの決定で解ける）

## 背景

`docs/specs/recommendation-evaluation/` の当日監視・事後分析は、今年（2026年）の MySQL を
読む必要がある。その経路が決まっていなかった（E-1）。

推薦エンジン側の ADR 0002 は「MySQL へ読み取り専用で直接接続する」を推奨し、
状態を「未決定（サーバー側の回答待ち）」としていた。

**しかし、その問いへの答えはすでにサーバー側に書かれていた。**

> 本番（さくら Standard）は外部から MySQL 直接接続不可のため、通常は
> `SAKURA_PROXY_URL` + `SAKURA_PROXY_KEY` を使う。
> — `event-support-server/docs/reference/environment-variables.md`

推奨案は成立しない。**回答が無かったのではなく、互いのドキュメントを見ていなかった。**

## 選択肢

| 案 | 内容 | 判定 |
|---|---|---|
| A | 既存のプロキシを、サーバーと同じ鍵で叩く | △ 鍵が全権。分析から `UPDATE` が通る |
| B | サーバーに読み取り専用の集計 API を足す | △ 指標ごとに改修が要る。1インスタンス固定のサーバーが経路に入る |
| C | MySQL へ直接接続 | ❌ さくら Standard では不可能 |
| **A′** | **プロキシに読み取り専用の口を1つ足し、分析・推薦にはその鍵だけを配る** | ⭐️ **採用** |

## 決定（案A′）

1. さくら側に**読み取り専用の MySQL ユーザー**を作る
2. そのユーザーに紐づく**プロキシの口と鍵をもう1組**用意する（さくら上の PHP に小さく追加。
   サーバー（Node）には触らない）
3. このリポジトリと推薦エンジンには、その鍵だけを配る

## 理由

**案A と案B の差の大半は「プロキシの鍵が全権であること」1点から来ている。**
経路をサーバーへ迂回させるのではなく、そこだけ直すのが最も安く済む。

- **集計の自由度が要る。** 当日監視の7指標のうち5つは既存の `analytics/*` API に無く、
  事後分析は本質的に反復作業である（個票ビュー・規則一覧・「なぜ変な値が出たか」の確認）。
  API 経由だと指標を足すたびにサーバー改修とデプロイを待つことになる
- **分析はアプリの API 経由にしない**のが一般的な作法である。API は画面のための契約であり、
  分析に必要な粒度を持たない
- **サーバーを経路に入れない。** Cloud Run は WebSocket のため `max-instances=1` に固定されている
  （サーバー ADR 0002）。当日のピーク2時間に、参加者のチェックインと同じインスタンスを使わない
- **推薦エンジンの ADR 0002 も同じ経路で解ける。** 1つ決めれば両方片づく
- 残る欠点（エラーが HTTP 500 に潰れる・イベント絞り込みを自前で書く）は、
  **クエリをテストで固定すれば実務上は許容できる**

## 影響

- `src/rec_db.py` の `SqlSource` をこの経路で実装する
- **イベントの絞り込み規則は `rec_db.py` の1箇所にだけ書く。** 指標・画面には書かない。
  `recommendation_scores` と `card_unlock_events` に `event_id` 列は無いため、
  `card_unlock_events` → `bingo_cards` を JOIN して絞る。
  **`users.event_id` では絞らない**（出展者・運営アカウントが混ざる）
- **事後分析はこの決定を待たない。** イベント後のダンプ1回で足りるため、
  CSV を書き出して `data/` に置く経路を別に確保する。E-1 が長引いても研究成果は守られる

## 未確認

**さくら Standard で、読み取り専用ユーザーとプロキシの口を追加できるかを確認していない。**

ただし、**確認のための往復を減らす形で用意した**（2026-08-31）。
プロキシ本体はどのリポジトリにも無く、さくら上に**先生**が設置している
（`event-support-server/docs/archive/orders/2026-06-09-…`）。そのため、

- 口の PHP・権限の SQL・設定の雛形を [`deploy/sakura-readonly-proxy/`](../../../deploy/sakura-readonly-proxy/) に置いた
- Docker で MySQL 8 と PHP 8 を立て、スキーマの正本を流して**実際に通してある**（33項目）
- 先生の作業は「ファイルを置く・SQL を1回流す・鍵を返す」の3つに縮めた

**読み取り専用ユーザーを作れなかった場合も止まらない。** その場合は既存の DB ユーザーで動かし、
書き込みは口の PHP 側の SELECT 判定だけで止める（壁が2枚から1枚に減る）。
案B（既存 `analytics/*` の拡張）へ落ちるのは、**口そのものを追加できなかったときだけ**である。
