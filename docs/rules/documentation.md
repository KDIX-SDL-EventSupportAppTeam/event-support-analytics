# ドキュメント運用

## 3つの棚

文書は**寿命**で分ける。迷ったら「この文書はいつ書き換わるか」で判断する。

| 棚 | 問い | 更新の仕方 |
|---|---|---|
| [specs/](../specs/) | **今どうあるべきか** | 決定が変わったら**上書きする**。過去の姿は残さない |
| [decisions/](../decisions/) | **なぜそうなったか** | **追記だけ**。過去の記録は絶対に書き換えない |
| [archive/](../archive/) | **昔はどうだったか** | 触らない。**参照しない** |

補助として [rules/](.)（守ること）と [operations/](../operations/)（手順）がある。

## 状態表記

`specs/` 配下のファイルは冒頭に必ず状態を書く。

```markdown
---
状態: 草案 | 確定 | 実装済み
最終更新: YYYY-MM-DD
---
```

**「確定」になっていない仕様は実装しない。** 未決定のまま実装に入りかけたら手を止める。

## リポジトリ間の原則

**仕様は「データを持つ側」に置く。**

| 内容 | 正本 |
|---|---|
| DB スキーマ・API 契約・ビジネスルール | `event-support-server` |
| 画面遷移・UI の見せ方・演出 | `event-support-frontend` |
| 推薦アルゴリズムの内部 | `event-support-recommender` |
| 指標の定義・分析手順 | `event-support-analytics` |

参照する側は**リンクだけ置き、内容をコピーしない**。

## 棚卸し

合言葉「**棚卸し**」でドキュメントの定期整理を行う。実施タイミングは、機能ひとつの実装が
終わったとき / 打ち合わせの直後 / 本番1ヶ月前。

1. `specs/` に「状態: 草案」のまま放置されたファイルがないか → 決めるか未決定リストへ移す
2. 実装済みの挙動と仕様書の記述が食い違っていないか → **コードを正として文書を直す**
3. もう使われていない仕様が `specs/` に残っていないか → `archive/` へ移す
4. 差分ドキュメントの項目が消化されたか → 済んだら `archive/` へ
5. 口頭で決めたことが `decisions/` に残っているか → 追記する
6. 指標の定義（`metrics.py`）と仕様書の記述がずれていないか
7. 未決定事項リストに、もう決まったものが残っていないか → `specs/` 本体へ昇格
8. 各仕様の「絶対にやることリスト」の消化状況を更新する
