# 取得できないデータ

**分析に着手する前に読むこと。** ここに挙げた項目は、
どれだけ工夫しても去年のデータからは得られない。時間を使う前に諦めるべきもの。

## 原理的に取得できない

### 入退場時刻

記録が存在しない。チェックインのみが時刻を持つ。

**代用**: 滞在時間を「最終チェックイン − 初回チェックイン」で近似する。

**この代用が持つ歪み**（結果を読む際に必ず考慮すること）:
- 受付から初回チェックインまでのラグが失われるため、**実際より短く出る**
- 最終チェックインから退場までのラグも失われるため、**さらに短く出る**
- 1ブースしか回っていない参加者は**滞在時間が定義上 0** になる

したがって算出される滞在時間は**真の滞在時間の下限**である。
「30分未満が X%」という結論は、真の値では X% より小さくなる。

### 同一ブースへの再訪問

`checkins` のドキュメントIDがブースIDであるため、再訪問は記録されない
（詳細は [firestore-schema.md](firestore-schema.md)）。

**当初の確認項目 E-4「同じブースへの複数回チェックインがあるか」は、
確認するまでもなく常にゼロである。この項目は削除する。**

同じ理由で、「ユニーク訪問数」と「チェックイン総数」を混同する危険も存在しない。
両者は構造上つねに一致する。

### 過去回とのユーザー紐づけ（リピーター率）

第1回・第2回の参加者を識別するIDが存在しない。

**本プロジェクトではリピーター分析を行わない**（分析対象外と決定済み）。

### 職業属性（学生 / 社会人 / 家族連れ）

`users` が保持する属性は `age` / `gender` / `genre` の3つのみ。
職業や同伴者の情報は収集されていない。

**代用**: 年代（`age`）を代理指標とする。ただし解像度は大きく落ちる。

### 事後アンケート

アンケート機能自体が存在しない。

**代用**: アワード投票を「事後アクション」の代理指標とする。
`user_status.vote_finalized` から算出される**投票確定率40.7%**が、
今年の評価入力の回収率を見積もる基礎として使える。

これは元の想定（アンケート回収率）より、むしろ直接的な参考値になる。

## 手作業が必要（自動取得できない）

### 会場マップ上のブース位置

去年のアプリは会場マップを画像（`frontend/public/map.png`）としてのみ保持しており、
ブースの座標データは存在しない。

「入口からの距離と訪問者数の関係」を見るには、
**40ブースに座標またはゾーンを手で振る必要がある**。作業量は30分程度。

**着手条件**: 先に D-1〜D-3（訪問者数の順位・倍率・集中度）を算出し、
**偏りが実際に存在することを確認してから**着手する。
偏りが小さければこの作業自体が不要になる。

### 訪問者が少なかったブースの共通点

出展内容・体験の重さなどは、
`booth_description` を読んで定性的に判断するしかない。定量化は不可能。

## 母集団についての注意

### アプリ登録者 ≒ 来場者

去年はイベントへの参加登録がアプリのログインを兼ねていたため、
`users` の302件は**ほぼ全来場者を捉えている**と考えてよい。

これにより「アプリ利用者しか見えない」というバイアスは、
去年のデータについては**問題にならない**。

### ただしチェックイン0件のユーザーが存在する

登録したがチェックインを一度も行わなかった参加者がいる。
また、ビンゴカードすら生成されていない参加者が8名いる。

**この層は「来場したがアプリを使わなかった層」として、
分析上むしろ積極的に数えるべき対象である。**
推薦機能が構造的に届かない層の規模を示すため、
[decision-criteria.md](../01-context/decision-criteria.md) の判断3に直結する。

訪問ブース数のヒストグラム（C-1）は、**必ず0件から始める**こと。
1件以上に絞ると、この層が見えなくなる。
