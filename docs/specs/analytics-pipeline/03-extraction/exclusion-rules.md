# 除外基準

分析対象から外すレコードの判定規則。
**除外は抽出時ではなく、中間テーブル生成時に行う。**
生データは無加工で保持し、除外の可否を後から検証できるようにする。

## 規則1: イベント期間外のレコード（最優先）

### 判定基準

```
2025-10-10 00:00 JST 〜 2025-10-11 23:59 JST の範囲外のチェックインを持つレコードを除外
```

### 根拠

`(default)` データベースは、10/27時点のクローン（`test1` / `test2`）と比較して
以下の差分を持つ。

| | 差分 |
|---|---:|
| users | +6 |
| checkins | +18 |
| awards | +13 |
| bingo_card | +64（= 4名分） |

これらはイベント終了から2週間以上経過した後に追加されたものであり、
**エクスポート機能のデバッグ中に作られたテストアカウント**と判断できる。

去年のリポジトリの最終コミットが「データエクスポート(失敗)」であることとも整合する。

### この規則の利点

当初「テストデータの目視判別が必要」と想定していたが、
**タイムスタンプによる機械的な除外で足りる**ことが判明した。
判断の主観が入らず、再現性がある。

### 注意

除外されたレコード数を必ず記録し、
上表の差分（ユーザー6名程度）と大きく食い違わないことを確認する。
食い違う場合は、イベント期間の定義かデータの解釈に誤りがある。

## 規則2: 運営・出展者アカウント

### 判定基準

自動判別できないため、以下の手がかりで候補を抽出し、**目視で確定する**。

**手がかり1: 開場前のチェックイン。**
一般来場者が開場前にチェックインすることはない。
初回チェックインが開場時刻より前のユーザーは運営の可能性が高い。

**手がかり2: 極端に多いチェックイン数。**
40ブース中30件以上など、明らかに一般来場者の行動から外れるもの。

**手がかり3: `㊳ PRoToFES BINGO` への早い時刻のチェックイン。**
これはアプリ制作チーム自身の出展ブースであり、
開場直後にここへチェックインしている場合は関係者の可能性がある。

### 運用

**除外候補として一覧を出力し、除外するかは人が判断する。**
自動除外はしない。誤って一般参加者を除外するリスクの方が大きい。

除外した場合は、除外したユーザー数と根拠を分析結果に併記する。

## 規則3: 外れ値の扱い

### 滞在時間が極端に長いレコード

**まず日跨ぎを疑う。**
去年は2日間開催のため、日別分割を行わずに
「最終チェックイン − 初回チェックイン」を計算すると、
両日参加者が24時間超になる。

日別分割後（[background.md](../01-context/background.md) 参照）も
なお長時間の外れ値が残る場合のみ、個別に中身を確認する。

### 除外しない

**外れ値は原則として除外しない。**
統計量（中央値・四分位）は外れ値に頑健であり、
ヒストグラムでは最上位ビンにまとめて表示すればよい。

除外するのは、規則1・規則2に該当するレコードのみとする。

## 除外の適用順序

```
生データ
  ↓ 規則1: イベント期間外を除外（機械的）
  ↓ 規則2: 運営・出展者を除外（目視確定）
  ↓ 「ユーザー × 日」に分割
分析対象データ
```

各段階でのレコード数を記録し、
最終的な分析対象が何名・何件になったかを明示すること。

## 除外しないもの

以下は**除外対象ではない**。分析上むしろ重要な対象である。

| 対象 | 理由 |
|---|---|
| チェックイン0件のユーザー | 「アプリを使わなかった層」の規模を示す（判断3に直結） |
| ビンゴカード未生成の8名 | 同上。より深刻な離脱層 |
| 単発訪問者（1ブースのみ） | 滞在時間0として別枠集計する（A-4） |
| 投票していないユーザー | 投票率の分母として必要 |

**訪問ブース数のヒストグラムは0件から始めること。**
1件以上に絞ると、これらの層が不可視になる。
