# 事後の分析画面

## 0. 原則

**問い1つにつき、決め手になる図を1つ。** 紐づかない図は作らない
（[analytics-pipeline の可視化原則](../analytics-pipeline/05-visualization/chart-spec.md) と同じ）。

当日画面（[03](03-live-dashboard.md)）とは**別のページ・別のファイル**にする。
重い集計を当日画面に混ぜると、信号機として機能しなくなる。

### 分析方針は事前に凍結する

**イベント前に主要指標・比較方法・除外規則・高評価の定義を紙に書いて固定する**
（`event-support-recommend/docs/specs/09-research-design.md` §5）。

事後に定義を変えて有意になるものを探すと、研究として成立しない。
**本ディレクトリの図は、凍結した定義に従って作る。**

## 2. 図① 訪問ブース数の ECDF（去年 vs 今年）

**ヒストグラムではなく累積分布（ECDF）にする。**
「分布が右にシフトしたか」の判定は ECDF のほうが読みやすく、
中央値だけでなく分布全体の動きが見える。

- 横軸: 訪問ブース数
- 縦軸: 累積割合
- 2本の曲線: **去年（金曜・192名）** と **今年**
- 中央値を図中に数値で書き込む（去年 6.0）

### 注意

- **去年は「ユーザー × 日」単位。金曜のみを代表日として使う**（302名は2日間の延べ）
- 去年・今年ともスタッフを除外する。去年は除外規則の扱いが違うので
  [FINDINGS.md](../../FINDINGS.md) §10 の未了項目を確認してから比較する
- **この図はアプリ全体の効果を示す。** 推薦アルゴリズムの効果とは別軸であることを注記する

## 3. 図② 参加者ごとの差のヒストグラム（実験の結論）

**この1枚が Q2 の結論になる。**

参加者ひとりにつき1点を打つ。

```
その人の差 = （DRSA 枠の訪問率） − （COVERAGE 枠の訪問率）

        0
        │
   ▁▃▅█│█▅▃▁        ← 0 を中心に対称 → 差なし
        │
      ▁▂│▅███▅▂     ← 右に寄る → DRSA が良い
```

- 縦線で 0 を明示する
- 平均（または中央値）を図中に数値で書き込む
- **対応のある比較**であることを明記する（同一人物の中での差）

### なぜ棒グラフではなくこれか

「DRSA 25% vs COVERAGE 17%」という棒グラフより説得力がある。
**同一人物・同一時刻・同一カードの中での差**であることが図の形から伝わるためである。

### 対象

**`attributes.arm` を持つ行のみ**（＝品質ゲート通過後の解放）。
分割前の枠は含めない。分割対象になった参加者数を注記する。

### 検出力の限界を注記する

各群 600〜700枠、訪問は各群100件前後。**検出できるのは 8ポイント程度の差まで。**
差が出なかった場合、「効果が無い」ではなく「**この標本では検出できなかった**」と書く。

## 4. 図③ `interest_match` 別のファネル（セレンディピティ）

```
                提示 → 訪問 → 評価 → 高評価
MATCH      :   ███████ → ███ → ██ → █
PARTIAL    :   █████   → ██  → █  → █
MISMATCH   :   ████    → █   → █  → ▌     ← 研究の主役
UNKNOWN    :   ██      → ▌   → ▌  → ▌
```

- 各段の**件数と歩留まり（前段からの割合）**を数値で書き込む
- `MISMATCH` の行を強調する

**`scores` を候補全件返している意味がここで効く。** 提示（分母）が取れているから、
一段ずつどこで落ちているかが見える。

> 「推薦しても行かない」のか「行ったけど気に入らない」のか——
> これが分離できると、次年度の改善方針が決まる。

### 比較対象

| 比較 | 何が言えるか |
|---|---|
| `MATCH` / `PARTIAL` の同じファネル | 一致カテゴリと比べてどうか |
| **カード外訪問（`cell_id IS NULL`）で不一致に行った率** | 推薦なしの自発訪問との比較（**参考値。因果は主張しない**） |
| 去年の自発訪問での不一致率 | [01](01-context.md) §3.1 のカテゴリ付与が前提。**評価が無いので「行った」まで** |

### 凍結値を使う

`interest_match` は**推薦した瞬間の値**が `recommendation_scores` に保存されている。
**再計算しない。** カテゴリは運営が当日でも編集できるため、後から計算すると値がずれる。

## 5. 図④〜⑥

### ④ 決定表件数帯別の訪問率

横軸に `card_unlock_events.decision_table_size` の帯、縦軸に推薦枠への訪問率。
「データ量が増えると推薦が良くなる」の傍証。

**フェーズ別に色分けしない。** フェーズは時刻と交絡しているため、
フェーズ別の比較は因果の主張にならない（[01](01-context.md) §2）。**記述にとどめる。**

### ⑤ 規則一覧

`rules_built` ログから、その日に生成された規則を表にする。

| 列 | 内容 |
|---|---|
| 規則 | `if preference_match >= 3 then 評価 >= HIGH` の形で表示 |
| 結論の向き | 上方 / 下方 |
| support / confidence | 生成時の値 |
| **発火回数** | `reason_payload.rules[].id` を突き合わせて数える |
| 存在した時間帯 | `rules_built_at` の範囲 |

**規則が人間に読める形で提示できること**が、DRSA を採用した理由そのものである
（`event-support-recommend` ADR 0001）。**論文にはこの表を載せる。**

### ⑥ `was_assigned=0` との比較

推薦されなかった候補のスコア分布と、推薦された候補のスコア分布を重ねる。
**「選ばれたものは実際に上位だったのか」**の確認。実装のサニティチェックも兼ねる。

## 6. 図⑦ 個票ビュー（1人の物語）

参加者を1人選ぶと、その人の全体が時系列で並ぶ画面。

```
u0042
 10:12 サインアップ / アンケート回答
       興味: AI・ものづくり / 第1希望: AI / 探索志向: mid
 13:05 カード生成。事前推薦マス: ブースB（AI）  ← 未訪問のまま
 13:20 チェックイン ブースK（フード）   中央マス①  評価3
 13:28 チェックイン ブースD（AI）       中央マス②  評価4
 13:28 【解放1回目】phase=DRSA  gate=passed
         枠1 [DRSA]     ブースX（ものづくり）  score 0.81  MISMATCH  規則 R12
         枠2 [COVERAGE] ブースY（フード）      score —     MATCH
 13:41 チェックイン ブースX  評価4  ★ MISMATCH かつ高評価 = セレンディピティ事例
 ...
```

### 3つの用途を同時に満たす

| 用途 | 内容 |
|---|---|
| **デバッグ** | データがおかしいとき、集計より速く気づける |
| **論文の説明** | 「実際にこういうことが起きた」という事例として使える |
| **サニティチェック** | **集計が正しくても個票が変なら実装がおかしい** |

**標本が数十件のオーダーしかない**（[01](01-context.md) §2）ため、
統計的な主張を厚くするより**事例の質を厚く見せる**ほうが有効である。
この画面はそのための素材になる。

### 注意

- **仮名 ID のまま扱う。** 実名・メールアドレスは扱わない（そもそも取得しない）
- 該当者が特定されうる絞り込み（属性の組み合わせ）と併用しない
  （[rules/data-handling.md](../../rules/data-handling.md)）

## 7. 実装

- **Streamlit**。当日画面とは別ファイルにする
- **指標の算出式は1箇所にまとめる**（既存の `metrics.py` の流儀を踏襲。二重管理しない）
- **条件属性・`interest_match` の計算は `event-support-recommend` の `features/` を
  import する。コピーしない**（`event-support-server` ADR 0004）
- 入力は DB からのダンプ（イベント後は一度きりで足りる）＋ JSONL ログ
