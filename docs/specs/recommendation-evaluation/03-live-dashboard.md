### 対応行動を画面に印字する

**当日は手順書を読み返す余裕が無い。**
各指標の隣に、上表の「何をするか」をそのまま短文で表示する。

### `/ops/state` が取れないとき

該当欄を「**取得不能**」と表示し、**他の指標は動かし続ける**。
`/ops/state` の取得失敗そのものが、フォールバック率と併せて障害のサインになる。

ただし **401 / 403（認証エラー）だけは「取得不能」と区別して表示する**。
本番の `/ops/*` は `X-Ops-Token` による認証が必須
（`event-support-recommend` ADR 0008）で、
analytics 側がトークンを送らなければ 401 が返り続ける。これは**こちら側の設定漏れ**であり、
「推薦エンジンが落ちている」とは打つ手がまったく違う。両者が同じ「取得不能」に丸まると
当日の切り分けができない。認証エラー時は「`RECOMMEND_OPS_TOKEN` を確認」と明示する。

- ヘッダは `X-Ops-Token`。`Authorization` は使わない（Cloud Run の IAM 認証と層を分ける）
- トークンは環境変数 `RECOMMEND_OPS_TOKEN`（推薦サービスの `OPS_TOKEN` と同一の秘密）
- base URL は環境変数 `RECOMMEND_BASE_URL` を既定にする。当日 URL を手打ちさせない
  （打ち間違いが認証エラー・接続失敗と同じ症状に見える）。サイドバーの入力欄は上書き用に残す
- `RECOMMEND_OPS_TOKEN` 未設定は取得を試みずに「未設定」と表示する（401 の「誤り」と区別）
- 失敗時は直近の正常値を取得時刻付きで別枠に出す。信号機の値は置き換えない

### パラメータ調整画面 `/demo` へのリンク

パラメータ調整のシミュレータ `/demo` は推薦側に置いたまま、この画面から**リンク1本で繋ぐ**
（`event-support-recommend` ADR 0008 案A。Streamlit へ移植し直さない）。
URL は `RECOMMEND_BASE_URL` から組み立てる。リンクの近くに必ず注記を置く:

- **シミュレータである。** 本番設定は Cloud Run の env が正で、変更にはデプロイが必要
- 開くには `RECOMMEND_OPS_TOKEN` が要る（この画面の合言葉とは別）

## 2. 画面2 — 当日の時系列

**1枚のグラフに重ねて描く。別々のグラフにしてはならない**
（[analytics-pipeline の B-2/B-3](../analytics-pipeline/05-visualization/chart-spec.md) と同じ流儀）。


- **設定を変更したら必ず縦線を引く。** 前後を別データとして扱うために要る

## 5. 当日に表示してはいけないもの

> **A/B の効果（DRSA 枠と COVERAGE 枠の訪問率の差）を当日に表示しない。**

見てしまうと、「DRSA のほうが悪いから設定を変えよう」という判断をしたくなる。
それをやると**実験が壊れる**（途中で条件を変えたデータは比較できない）。
**無意識にやってしまうのが怖い。**

| | |
|---|---|
| ✅ 表示してよい | 各群の**提示数**（§4） |
| ❌ 表示しない | 訪問率、およびその**差** |

効果は当日の行動に何も影響しない。**隠しても失うものが無い。**

実装上も、当日画面のコードに訪問率の群別集計を**書かない**。
「あとで見ないようにする」ではなく、**最初から計算しない**。

## 7. タブ構成（2026-10-13 追加）

読み手がエンジニアに変わったため、当日画面をタブに分けた。**当日の判断は「🚦 信号機」タブだけで足りる**
（§1〜§5 はそのまま）。他の2タブは「いま推薦の中で何が起きているか」を説明するためのもの。

| タブ | 中身 | 算出 |
|---|---|---|
| 🚦 信号機 | §1〜§5 | 既存 |
| 🧠 推薦エンジンの中身 | 段階（アンケート → ランダム期 → DRSA 期）と現在地、DRSA までの残り件数と到達見込み時刻（直近30分の評価ペース）、品質ゲート4条件の現在値としきい値、マスの選ばれ方（RANDOM/DRSA/SER/EXPLORE）、SER の進捗、決定表（条件×高評価率のヒートマップ）、推薦の調子（訪問率・推薦経由とカード外の高評価率・関心一致度別の訪問率） | `live_metrics.engine_overview` ほか |
| 👥 参加者とブース | 参加者数・直近30分に動いた人・10分ごとのチェックイン・1人あたり訪問数・ブース別の訪問と平均評価 | `live_metrics.participant_overview` / `booth_popularity` |

- 品質ゲートのしきい値（規則2本・γ0.5・被覆率0.5）は `/ops/state` が返さないため、推薦側 `settings.py` の既定値を `live_metrics.GATE_DEFAULTS` に写している。推薦側で変えたら合わせる
- 決定表は推薦スコアの `attributes.condition` で再現した**近似**。エンジン内部の件数とずれうる
- **A/B（DRSA 枠と COVERAGE 枠）の比較はこのタブにも出さない**（§5）。推薦経由とカード外の比較は群別ではないので出す

### JST 保存列の補正

DB 既定値で入る列（`rated_at`・`card_unlock_events.created_at`・`recommendation_scores.created_at`）は JST で保存されている
（[02 §2.1](02-data-source.md#21-タイムスタンプの時刻帯が列によって違うさくら-db)）。補正前は直近の解放が「9時間後」扱いになり、
**「直近30分の解放数」が常に0件（🔴）、フォールバック率が「直近の解放が無い」になっていた。**
`rec_db.load_tables` が `align_db_default_timestamps` で、評価とチェックインの時刻差（約 +9 時間なら JST）を見て UTC に直す。
