# 推薦の評価 — 当日の監視と事後の分析

**2026年 第4回プロトフェス（10-16 金）の推薦システムを、当日は壊れていないか監視し、
事後は研究として分析するための仕様。**

`analytics-pipeline/` が**去年（2025年）のデータを分析する**仕様であるのに対し、
本ディレクトリは**今年（2026年）のデータを扱う。** このリポジトリの守備範囲の拡張である。

## 貫く原則

`analytics-pipeline/05-visualization` の原則をそのまま引き継ぐ。

> **「見て面白い図」ではなく「見た結果として設計が変わる図」だけを作る。**

本ディレクトリではこれを2つに分けて適用する。

| | 当日（03） | 事後（04） |
|---|---|---|
| 目的 | **壊れていないか** | 何が起きたか |
| 判断 | その場で打てる手が3つある（§03） | 論文に何を書くか |
| 設計 | **信号機。対応行動を画面に印字する** | 問い1つに図1つ |
| データ源 | **DB**（推薦エンジンに依存しない） | DB ＋ 推薦エンジンの JSONL |
| 更新 | 30〜60秒の自動更新 | オンデマンド |

**当日、対応する行動が無い数字は載せない。** 事後に回す。

## 絶対に守ること

1. **当日に A/B の効果（訪問率の差）を表示しない。**
   見ると設定を変えたくなり、実験が壊れる。**分母（提示数）だけ表示する**（[03](03-live-dashboard.md) §5）
2. **当日ダッシュボードは推薦エンジンに依存させない。**
   推薦エンジンが死んでいるとき、その `/ops/state` も死んでいる（[02](02-data-source.md) §1）
3. **去年データを今年の対照群として使わない。**
   ビンゴの仕組み自体が変わっており、アルゴリズムの効果と分離できない（[01](01-context.md) §3）
4. 個人データを保存しない・仮名 ID のまま扱う（[rules/data-handling.md](../../rules/data-handling.md)）

## 推薦エンジン側の仕様との対応

観測データを**出す側**の仕様は `event-support-recommend` にある。

| 向こうのファイル | 内容 |
|---|---|
| `docs/specs/10-observability.md` | `/ops/state` の中身、JSONL ログ、当日の対応行動 |
| `docs/specs/09-research-design.md` | 実験設計（参加者内ランダム化）・標本サイズ・凍結する分析方針 |
| `docs/specs/03-phases.md` | フェーズと品質ゲート |
| `docs/specs/02-features.md` | 条件属性の定義（**`features/` を import して使う**） |

**指標の計算に使う特徴量は、推薦リポジトリの `features/` を import する。コピーしない。**
「分析で使った定義と本番の推薦が違う」という事故を構造で防ぐため
（`event-support-server` ADR 0004）。
